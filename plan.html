01

Revision history

R3

Redis deferred — realtime state goes in memory, behind an interface

The engineering guidelines rule against introducing Redis for scalability alone, and they are right: with one Node process and ten users a Map is simpler, faster and one less service to secure. Phase 06 now defines a PresenceStore interface with an in-memory implementation. Redis becomes a second implementation of the same interface on the day a second server instance exists.

R3

Auth moves to Better Auth, with the org model still in our Postgres

Hand-rolled sessions were the highest-risk part of phase 02. Better Auth's organization plugin generates orgs, members, invitations and roles as tables in our own database — so the tenant boundary and the seat count for billing keep a single source of truth, which a vendor-hosted org model could not offer without a sync gap.

R3

Art is Kenney CC0 for V1, loaded through an asset manifest

Prototype on CC0 art with zero licence obligations, buy a better pack once the product is validated. Every asset is referenced through a manifest that carries tile size and frame layout, so swapping a 16×16 free pack for a 32×32 paid one is a manifest edit, not a code change.

R2

Multi-tenancy moves into the first schema, not "someday"

Rev 1 built one office and listed multiple organizations as out of scope. Adding organizations above offices now costs half a day. Retrofitting it after auth, Redis keys, socket rooms and LiveKit room names all assume a single office costs weeks. You can still ship one office in the UI.

R2

Proximity is selective subscription, not connect/disconnect

Rev 1 said "connect/disconnect based on nearby users" — that is the peer-to-peer mental model and it produces exactly the connection churn Rev 1's own optimization list worried about. With an SFU, nobody ever connects or disconnects. Everyone joins one room and you toggle track subscriptions.

R2

The map is data, not code

The office editor stays out of V1, but the map ships as a Tiled JSON document loaded at runtime. If the map lives in Phaser scene files, the editor is a rewrite later. Custom offices are the thing that stops customers churning.

R2

Track B: chat, recordings, transcription, AI notes, integrations

Proximity video is a feature now, not a product. Phases 17–23 add async chat, recording, AI meeting notes, Calendar / GitHub / Spotify, billing, and SSO — the layer that makes this sellable rather than a demo.

R2

A recorded decision log and a UI production method

Sections 3 and 7. Every stack choice now carries its reasoning, so the next engineer does not relitigate it, and the UI has a named split between the DOM layer and the canvas layer.

02

What done means

Ten real people run their daily standup inside the office, simultaneously, for a full working week — with no crashes, no desync, no broken audio, and nobody dropping to Google Meet as a fallback. That last clause is the honest test.

Track A gate. Do not start Track B until Track A has survived five consecutive standups without manual intervention. Shipping chat on top of a flaky presence system just gives you two broken systems.
Track B gate. One team outside your own uses the product for two weeks and would notice if it disappeared. That is the signal that there is something to sell; everything before it is a prototype with good uptime.
03

Decisions on record

ChoiceDecisionWhy, and what was rejected
Database PostgreSQL The data is relational to its core: org → office → member → role → seat, and every read is scoped by org and joined through membership. Seat-based billing needs transactional integrity and cross-row uniqueness that a document store cannot enforce. Postgres also gives row-level security as a real multi-tenant safety net, JSONB for map and config documents, and pgvector later for searching meeting notes. MongoDB rejected — Gather uses it because it was 2020's default, not because it fits. The one workload Mongo would win is high-frequency transient writes, and those never reach the database at all — they live in the in-memory presence store.
Media LiveKit Cloud Managed SFU with selective subscription, per-participant volume, simulcast, and egress for recording — every primitive the proximity engine and Track B need. Own SFU rejected for now: Gather built theirs in 2020 because nothing like LiveKit existed. Revisit only when per-minute cost becomes a real line item, and treat it as an infrastructure project, not a feature.
Renderer Phaser 4.2.1 Verified against npm at pin time — v4 is the current stable line, not v3 as this plan first said. Its breaking changes are confined to custom WebGL pipelines, filters, BitmapMask and Geom.Point; tilemaps, Arcade physics, sprites, input and cameras are unchanged, which is our entire surface. Tilemaps, collision, camera and sprite animation out of the box, which is most of Track A phase 03. PixiJS noted as the exit: if the canvas becomes the product surface and Phaser's game-loop assumptions start fighting you, Pixi is the migration — it is what Gather appears to sit on. Keeping the map as data makes that migration survivable.
Tenancy Org-scoped from schema one Every table carries org_id, and every socket room, presence-store key and LiveKit room name is namespaced by it. Costs half a day now; costs a rewrite later.
Auth Better Auth Its organization plugin generates orgs, members, invitations and roles as tables in our Postgres, with server APIs and a typed client. That keeps the tenant boundary and the billing seat count on one source of truth. Clerk and WorkOS rejected for now — both hold the org model on their side, which means mirroring it into Postgres and accepting a sync gap on a hard security boundary. Hand-rolled rejected: sessions, rotation and reset are where custom auth quietly goes wrong. Trade-off accepted: no hosted SAML, so phase 23 adds WorkOS purely as an SSO layer in front. Better Auth writes no audit trail — we build that ourselves.
Realtime state In-memory, behind an interface One Node process and ten users does not need a second datastore. A PresenceStore interface holds positions, sockets and heartbeats in a Map; Redis is deferred to a second implementation of that same interface, added the day a second server instance exists and Socket.IO needs a cross-process adapter. State is lost on restart by design — clients resync on reconnect, and phase 15 tests exactly that.
Art Kenney CC0, then paid Public-domain art carries no attribution or share-alike obligation, so V1 prototypes with zero licence surface. Every asset resolves through a manifest carrying tile size and frame layout, making the later swap to a richer 32×32 pack a manifest edit. LPC rejected — CC-BY-SA is copyleft on derived sprite sheets, and its wardrobe is medieval rather than modern office.
Language TypeScript, end to end One package of shared types for realtime events, API payloads and DB models, validated at both edges with Zod. Realtime bugs are mostly contract bugs.

Revised

Schema

034–6 days

2D world, map as data

Revised

A complete single-player office with zero networking, so movement bugs stay movement bugs.

Map format
  • Authored in Tiled, exported as JSON
  • Tileset, floor, walls, furniture layers
  • Collision from tile properties
  • Zones as object rectangles with metadata
  • Spawn points as named objects
  • Stored in Postgres JSONB, fetched at runtime
Avatar
  • Sprite sheet with four-direction walk
  • Name label and status dot
  • WASD and arrow keys
  • Collision against the wall layer
  • Camera follow with soft bounds
  • Locked 60fps budget
Rule: nothing about the map is hardcoded in a scene file. A new office should be a new JSON row, not a deploy.
Asset manifest. V1 art is Kenney's CC0 packs — RPG Urban for tiles, Roguelike Characters for avatars — chosen because public-domain carries no attribution or share-alike obligation while we are still validating. Everything loads through one manifest mapping logical names (avatar.walk.down, tile.desk) to files, frame rects and tile size. Game code never names a file, and tile size is read from the manifest rather than hardcoded, so replacing 16×16 CC0 art with a paid 32×32 pack is a manifest edit plus a re-slice. Half a day now; a refactor otherwise.

Events

  • PLAYER_JOINED / PLAYER_LEFT
  • ZONE_ENTER / ZONE_EXIT
  • PRESENCE_UPDATE
  • STATE_SNAPSHOT on join

  • Rejoin restores full state, not diffs
062–3 days

Realtime state store

Rewritten

Hot state out of Postgres, in one process, behind a boundary Redis can step into later.

Holds
  • Socket id → user, org, office
  • Current position and facing
  • Zone membership
  • Last heartbeat timestamp
  • Presence status
Rules
  • One PresenceStore interface, nothing else touches state
  • MemoryPresenceStore — keys still namespaced by org
  • Sweeper interval for stale connections
  • Duplicate login evicts the older socket
  • No query inside the movement loop
  • Lost on restart, by design
Why Redis is not here. With a single Node process, a Map is faster, simpler, and one less service to run, secure and pay for. Redis earns its place the day a second instance exists — at which point Socket.IO also needs a cross-process adapter, and both arrive together as one deliberate change. Building the interface now costs almost nothing and makes that swap a new class rather than a refactor. State surviving a restart is not a V1 requirement: clients resync on reconnect, and phase 15 tests that explicitly by killing the server mid-session.
072–3 days

Presence

Status people can trust without asking in chat.

States
  • Online — socket alive, heartbeat fresh
  • Away — no input past threshold
  • In meeting — inside a zone
  • Focus — manual, suppresses proximity audio
  • Offline — heartbeat expired
Behaviour
  • Derived server-side, never client-asserted
  • Debounced so it does not flicker
  • Broadcast only on change
  • Visible on avatar and in the roster
084–7 days

LiveKit media layer

Voice, video and screen share, before any spatial logic touches it.

Server
  • Short-lived tokens, minted per join
  • Room name org_{id}_office_{id}
  • Grants scoped to verified membership
  • API secret never leaves the server
  • Webhook handler for room events
Client
  • Join with autoSubscribe: false
  • Publish mic on join, camera on demand
  • Device picker and permission prompts
  • Mute, camera toggle, screen share
  • Simulcast enabled for video
  • Connection quality surfaced in UI
The one line that matters: autoSubscribe: false. Everyone in the office joins the same room, but subscribes to nothing by default. Phase 09 is entirely about deciding what to subscribe to.
094–6 days

Proximity engine

Rewritten

Walk near someone and hear them — implemented as subscription state, never as connection state.

The loop
  • Recompute at 5–10Hz, not per frame
  • Squared distance — skip the square root
  • Grid buckets once past ~30 avatars
  • Diff against last tick; act only on change
The rules
  • Audio subscribe at r_in, drop at r_out
  • r_out > r_in — hysteresis kills flapping
  • Full volume inside r_core
  • Linear falloff r_core → r_out via setVolume()
  • Video on a tighter radius than audio
  • Cap concurrent video to nearest N (start at 6)
  • Drop simulcast layer as distance grows
Why this replaces Rev 1's model: connecting and disconnecting peers at a boundary means renegotiation every time someone paces at the edge of a radius — the churn the old plan flagged but could not solve. Toggling setSubscribed() on an existing SFU connection costs nothing and needs no renegotiation. Two radii plus hysteresis is the whole fix.
103–4 days

Zones and the standup room

Bounded spaces that override the distance rules.

Behaviour
  • Zone rectangles come from the map JSON
  • Server authoritative on enter and exit
  • Inside: subscribe to all members regardless of distance
  • Inside: hard-mute everyone outside
  • Outside: zone occupants are inaudible
  • Presence flips to In meeting
Zone types
  • Standup room — everyone equal
  • Private booth — capacity 2–4
  • Desk — solo, proximity suppressed
  • Quiet area — no audio at all
Milestone: the full team walks into the standup room and runs a real meeting with voice and video. This is the first day the thing feels like a product.

Async chat

New

The office is empty at 3am. Chat is what makes it worth opening anyway.

Model

  • messages — threaded via parent id
  • reactions, read_state per user
  • DMs as two-member channels

Behaviour

AI meeting notes

New

The transcript nobody reads, turned into the summary everybody does.

Generation

  • Summary, decisions, action items with owners
  • Open questions and follow-ups
  • Every claim cites its transcript timestamp

07

How the UI gets built

The interface is two different problems wearing one screen, and conflating them is the mistake that makes this slow. Split them explicitly and tool each one differently.

Layer one

DOM — React

Auth, roster, chat, controls, settings, admin, marketing. Roughly 70% of the work. Conventional web UI, and every tool below applies.

Layer two

Canvas — Phaser

Map, avatars, movement, zone overlays, proximity indicators. Hand-written. No design tool reads a canvas, and no MCP will generate it for you.

Tooling that actually helps, and where

ToolLayerWhat it does for this project
Claude DesignDOMThe /design canvas in this session. Lay out the office shell, roster, chat panel and settings as artboards, adjust them visually, then build from the agreed layout. Cheapest place to resolve a layout argument.
shadcn/ui + MCPDOMComponent source of truth. You own the code, so restyling the whole app later does not mean fighting a vendor's theme. The MCP lets the agent pull real component source instead of approximating it.
Playwright MCPBothThe highest-value one here. Drives real browsers, so it verifies UI changes — and the same harness runs the ten-client load test in phase 15. Build the multi-client rig once and use it for both.
Chrome DevTools MCPCanvasFrame profiling. Phaser plus a proximity loop plus ten video tiles is a real frame budget, and this is how you find what is eating it.
Figma Dev Mode MCPDOMOnly worth it if design genuinely lives in Figma. If it does not, skip it — do not adopt Figma just to have an MCP for it.
Context7 MCPBothCurrent docs for LiveKit and Phaser. Both move faster than model training data, and LiveKit's subscription API in particular is easy to get subtly wrong from memory.
The honest limit: none of these help with the canvas layer, which is the part that makes the product feel like a place rather than a webpage. Budget real hand-written time for tile art, avatar animation and movement feel. Buy or commission the sprite set — a 16×16 or 32×32 asset pack costs a weekend of your time and looks better than what you would draw.
